# API 与数据约束

## API

- API 使用版本化 JSON/REST 契约；路径、请求/响应 schema、错误码和认证要求进入 OpenAPI，并由服务端类型生成。
- 所有输入在服务端做类型、长度、范围、枚举、关联记录和状态校验。未知字段策略需一致；错误响应不得返回堆栈、SQL、令牌或内部作者字段。
- 区分未认证（401）、无权（403）和资源不可见/不存在（按统一防枚举策略处理）；列表、详情、搜索、计数和聚合都必须执行相同授权与可见性规则。
- 分页使用有界 page size 和稳定排序；公开筛选/排序参数采用白名单，避免任意 SQL 字段拼接。
- 写操作定义幂等性/重复提交行为；并发点赞、收藏、举报和评价创建依靠数据库约束保证一致性。
- 面向客户端的 DTO 显式列字段，不直接序列化数据库实体。匿名内容响应不得含 `author_id`、学号、邮箱或可逆的内部关联标识。

## 数据与持久化

- 主键、时间戳、外键、唯一约束、非空规则和索引由迁移管理；迁移按可审阅的小步提交，提供升级路径，破坏性变更说明数据回填/回滚策略。
- 时间戳持久化 UTC；展示时按用户/产品时区格式化。年份是独立可空整数，不用日期哨兵值表示“未注明”。
- 课程关联指向有效课程记录；标签引用平台维护的有效词典。图片 URL/对象 key 不可信，数量上限为 9。
- `author_id` 等内部字段不得因响应复用而暴露。后台访问匿名作者关联要经过单独授权并留下审计记录。
- 删除、下架和审核状态分别表达，不用删除记录代替审核状态；保留期限待产品/法务确认。需要聚合的评分只纳入有效且符合状态规则的评价，经验帖永不纳入。
- 金额/积分等本期排除数据不得预建为无用途的核心模型。

## 事务与状态

状态转移必须显式定义允许的前后状态及触发者。审核通过/拒绝、发布/下架和账号停用等复合操作在一个数据库事务内写入状态与必要的审计记录。异步副作用（邮件/通知）失败时不得回滚已完成的核心状态；记录可重试结果，具体任务机制按架构约束准入。
