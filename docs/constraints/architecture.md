# 架构与依赖约束

## 建议基线

项目尚无实现，以下为首版建议基线，落地前检查仓库环境与兼容性；一旦形成可运行实现，应以锁定文件和实际代码为准并同步修订本文件。

- 后端：Go 1.26、`net/http`、chi v5，模块化单体。
- 数据库：PostgreSQL 16、pgx v5、手写 SQL、goose 迁移。
- API：JSON/REST；Huma v2 生成 OpenAPI 3.1。移动端用 `openapi-typescript` 生成接口类型，生成物注明来源且不得手工修改。
- 移动端：Expo SDK 54、React Native 0.81、React 19、TypeScript 5.9 strict、Expo Router 6。依赖版本以实际兼容性验证和锁文件为准。
- TanStack Query 管理服务端状态；`expo-secure-store` 保存会话凭据。优先 Expo 托管原生能力。
- 图片存储先抽象接口，开发环境本地存储；部署目标确认后再选兼容 S3 的实现。

这些版本可能随环境和维护状态变化。新增工程时核验官方支持矩阵、当前机器可用工具和仓库锁文件，避免仅因本文件列出版本而强制采用不兼容版本。

## 模块边界

按业务能力划分身份与会话、课程目录、评价、经验帖、互动/通知、举报审核等模块。模块通过明确的服务接口协作；跨模块写入必须说明事务边界和失败处理。避免按页面复制业务规则，也避免为了分层而增加空壳抽象。领域校验放在服务端用例/领域层，HTTP handler 负责协议转换。

## 基础设施准入

首版默认不依赖 Redis、PostGIS、独立消息队列/worker、独立搜索引擎、云推送、第三方监控或容器编排。通知先持久化在数据库。确有需求时，说明产品需求、现有方案不足、故障/运维成本和回退策略，再调整架构约束。

本地 PostgreSQL 可用 Docker Compose；不得为了开发便利把生产密钥写入 compose 文件或提交仓库。邮件配置来自环境变量/部署密钥管理。对开发、测试和生产配置分别给出安全默认值。

首版的验证码发件方暂用项目负责人指定的个人邮箱；只在本地忽略文件或部署密钥配置中保存地址和 SMTP/API 凭据，不提交真实值。课程导入文件首版支持 CSV 与 `.xlsx`，导入解析应限制文件大小并提供预览和逐行错误报告；不需要为导入引入独立服务。

## 依赖原则

引入依赖前核实维护状态、许可证、平台兼容性、安全更新和替代方案。优先标准库和现有依赖；不因单一简单功能引入大型框架。新增依赖同步更新锁文件、运行说明及本文件。不要把全局 CLI 或本机偶然安装作为构建前置条件。
