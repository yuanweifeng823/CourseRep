# 质量与交付约束

## 实现要求

- 沿用仓库实际语言、格式工具、目录与命名约定；无既有约定时采用最小且一致的方案。
- 代码应覆盖正常、空、错误、权限拒绝和边界输入路径；服务端校验为权威，客户端校验仅用于即时反馈。
- 数据库变更、OpenAPI schema 和生成客户端类型保持一致。生成产物注明生成命令与来源，避免手工修改。
- 配置通过环境或受控配置注入；提供不含秘密的 `.env.example`（需要时）和本地运行说明。
- 不提交真实用户数据、密钥、构建缓存或本地数据库文件。示例/fixture 使用虚构信息。

## 验证

根据改动选择并实际运行相关格式检查、静态分析、单元/集成测试、迁移检查和构建。涉及授权、匿名、审核状态、年份空值和上传时，验证对应服务端边界。依赖服务不可用时，说明未运行的项目和原因；不得把“应当通过”描述成已通过。

当前仓库没有代码或自动化配置，因此首轮只可核对文档一致性；当代码和工具建立后，补齐可重复执行的检查脚本及 CI 规则。新增测试必须针对具体行为，避免无目的测试框架堆叠。

## 变更与交付

- 变更范围聚焦任务；数据 schema、API、配置、依赖和产品行为变化应在 PR/提交说明中点明兼容性及回滚影响。
- 更新需求、约束、运行说明和生成产物的来源说明，使其与实现一致。对未决政策保留明确标记。
- 完成交付时列出修改文件、实际行为影响、执行过的验证及结果、未解决的假设/风险；没有代码变更时明确说明。
- 不因“标准化”进行无关重构或引入额外基础设施。
